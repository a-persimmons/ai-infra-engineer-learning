# 行为准则

## 我们的承诺

作为社区成员、贡献者和领导者，我们承诺让每个人都能够在不受骚扰的环境中参与社区活动，不因年龄、体型、可见或不可见的残障、族裔、性别特征、性别认同和表达、经验水平、教育背景、社会经济地位、国籍、个人外貌、种族、宗教、性身份或性取向而受到区别对待。

我们承诺以有助于建立开放、友好、多元、包容和健康社区的方式行事和交流。

## 我们的标准

### 积极行为

有助于营造积极环境的行为示例：

- **尊重他人**：尊重并体谅每一个人。
- **热情接纳**：欢迎新成员，帮助他们入门。
- **协作**：共同工作，分享知识。
- **耐心**：每个人都有自己的学习节奏。
- **建设性**：提供有帮助且可操作的反馈。
- **同理心**：理解不同的观点和经历。
- **专业性**：在所有交流中保持专业。
- **认可贡献**：承认他人的贡献和想法。

### 不可接受的行为

- **骚扰**：任何形式的骚扰、恐吓或欺凌。
- **歧视**：歧视性的玩笑、语言或行为。
- **人身攻击**：针对个人而非其观点进行攻击。
- **恶意挑衅**：故意发表煽动性或偏离主题的评论。
- **侵犯隐私**：未经许可分享他人的私人信息。
- **性相关内容**：不受欢迎的性关注或性示好。
- **垃圾信息**：过度自我推广或无关内容。
- **不诚实**：抄袭、冒充他人或其他欺骗行为。

## 我们的责任

### 维护者

项目维护者负责：

- 明确并执行可接受行为的标准。
- 采取适当、公平的纠正措施。
- 删除、编辑或拒绝违反本行为准则的贡献。
- 在适当情况下说明管理决定的原因。

### 社区成员

社区成员应：

- 阅读并遵守本行为准则。
- 向项目维护者报告违规行为。
- 支持友好且包容的环境。
- 坦然接受建设性反馈。
- 关注社区的整体利益。

## 适用范围

本行为准则适用于：

- 所有项目空间（仓库、Issue、Discussion、Pull Request）。
- 官方沟通渠道（Slack、邮件列表）。
- 线上或线下活动及聚会。
- 代表项目时使用的社交媒体。
- 其他任何社区互动。

在公共空间代表本项目时，本准则同样适用。

## 执行

### 举报违规行为

如果你遭遇或目睹不可接受的行为：

1. **向维护者举报**：发送邮件至 conduct@ai-infra-learning.org（或提交保密 Issue）。
2. **提供详细信息**：说明发生了什么、时间、地点和涉及人员。
3. **具体描述**：如有可能，附上链接、截图或其他证据。
4. **保持保密**：举报将得到审慎处理。

### 举报应包含的信息

- 你的联系方式。
- 涉及人员的姓名。
- 事件描述。
- 日期与时间。
- 背景及具体情况。
- 任何支持性证据。
- 其他相关信息。

### 执行流程

1. **审查**：维护者审查举报。
2. **调查**：必要时收集更多信息。
3. **决定**：确定适当的处理方式。
4. **行动**：执行相应措施。
5. **跟进**：监测是否再次违规。

### 违规后果

违规可能导致：

**1. 警告**
- **措施**：私下书面警告。
- **适用情况**：首次轻微违规。
- **期限**：记入记录。

**2. 临时封禁**
- **措施**：暂时停止参与社区活动。
- **适用情况**：多次轻微违规或一次中度违规。
- **期限**：7 天至 3 个月。

**3. 永久封禁**
- **措施**：永久禁止参与社区。
- **适用情况**：严重违规，或警告后仍反复违规。
- **期限**：无限期。

### 申诉

如不同意处理决定：

1. 在 7 天内向 appeals@ai-infra-learning.org 发送邮件。
2. 说明你认为决定不正确的原因。
3. 维护者将在 14 天内审查并回复。
4. 申诉决定为最终决定。

## 具体场景

### Discussion 和 Issue

**应该：**
- 清楚提问并提供背景。
- 发帖前搜索已有讨论。
- 感谢提供帮助的人。
- 问题解决后标记解决方案。
- 使用适当的标签。

**不应该：**
- 要求立即回复。
- 重复发布同一问题。
- 偏离主题。
- 进行没有进展的争论。
- 使用全大写英文（缩写除外）。

### Pull Request

**应该：**
- 清楚描述变更。
- 建设性地回应反馈。
- 提交前测试代码。
- 遵循贡献指南。
- 耐心等待评审。

**不应该：**
- 将代码批评视为人身攻击。
- 提交不完整或未经测试的代码。
- 忽略评审意见。
- 未经讨论进行重大变更。
- 围绕风格偏好争论（遵循项目标准）。

### 代码评审

**应该：**
- 关注代码而非个人。
- 解释建议背后的原因。
- 认可优秀的工作。
- 通过提问交流，而非提出命令。
- 建议替代方案。

**不应该：**
- 使用严厉或带有评判性的语言。
- 不加解释地否定他人的疑虑。
- 因轻微风格问题阻止 PR。
- 无正当理由要求修改。
- 评审自己的代码（利益冲突）。

### 寻求帮助时

**应该：**
- 先搜索文档。
- 提供最小可复现示例。
- 附上错误信息及日志。
- 说明运行环境。
- 展示已尝试的方案。

**不应该：**
- 期待别人替你完成工作。
- 对提供帮助的人表现出不耐烦。
- 忽略后续问题。
- 在多个渠道重复发帖。
- 直接提醒维护者（使用公开渠道）。

### 帮助他人时

**应该：**
- 对初学者保持耐心。
- 提供解释，而不仅仅是答案。
- 指向相关文档。
- 鼓励学习。
- 肯定进步。

**不应该：**
- 让他人觉得自己愚蠢。
- 说「自己去 Google」。
- 只给解决方案而不解释。
- 按知识水平设置参与门槛。
- 不必要地使用行话。

## 包容性语言

### 推荐用语

- 性别未知时使用 they/them。
- 使用 allowlist/denylist，而不是 whitelist/blacklist。
- 使用 primary/replica，而不是 master/slave。
- 使用 folks 或 everyone，而不是 guys。
- 使用以人为先的措辞，例如 person with disability，而非 disabled person。

### 避免

- 带有性别假设的语言（假定每个人都是男性）。
- 带有残障歧视色彩的语言（crazy、lame、blind spot）。
- 暴力隐喻（kill the process → stop the process）。
- 文化假设（并非每个人都庆祝相同节日）。
- 难以翻译的习语。

## 冲突解决

### 如果你有不同意见

1. **假设对方出于善意**：大多数冲突来自误解。
2. **直接沟通**：首先与对方私下交流。
3. **关注问题而非个人**：批评观点，而非个人。
4. **寻求理解**：作出判断前先提问。
5. **寻找共识**：寻找双方同意的方面。
6. **妥协**：愿意寻求折中方案。
7. **引入调解人**：如果直接沟通无效。

### 如果你犯了错误

1. **承认错误**：承认自己有误。
2. **道歉**：真诚表达歉意。
3. **弥补**：修复造成的伤害。
4. **从中学习**：不要重复同样的错误。
5. **向前看**：不必无谓地纠结。

### 如果他人犯了错误

1. **善意理解**：假设并非有意为之。
2. **友善引导**：解释为什么存在问题。
3. **接受道歉**：不要怀恨在心。
4. **以身作则**：展示适当的行为方式。
5. **向前看**：关注改进，而非惩罚。

## 创建包容的环境

### 面向初学者

- 提供对初学者友好的文档。
- 使用 good first issue 标签标记入门任务。
- 提供指导机会。
- 肯定首次贡献。
- 耐心回答基础问题。

### 面向多元背景的贡献者

- 使用包容性语言。
- 留意时区差异。
- 接纳不同的沟通方式。
- 认识文化差异。
- 提供多种贡献方式。

### 面向所有人

- 鼓励不同背景的人参与。
- 让代表性不足的群体获得更多表达机会。
- 发现偏见时提出质疑。
- 创建安全的讨论空间。
- 认可多样化的贡献。
