## 问题 1
**问题：** ML 基础设施工程师的主要职责是什么？

**答案：** B) 构建和维护支持 ML 模型部署与运行的系统

**解析：**
ML 基础设施工程师是平台构建者，而非模型构建者。他们负责创建训练集群、模型服务基础设施、数据流水线和监控等系统，使数据科学家及 ML 工程师能可靠地将模型投入生产。实现高模型准确率（A）、发明新算法（C）、提取业务洞察（D）分别属于 ML 研究人员、应用科学家与数据分析师的职责。

**常见错误：**
- 因为职位名称中包含“ML”而选择 A，认为该职位以训练模型为核心；事实上，基础设施工程师很少亲自训练生产模型。
- 将该职位与数据科学家（D）混淆，后者关注生成洞察，而非系统可靠性和可扩展性。

**相关资料：** `lessons/mod-101-foundations/01-introduction.md`

## 问题 2
**问题：** 以下哪项不属于 ML 生命周期的阶段？

**答案：** C) 客户获取

**解析：**
ML 生命周期涵盖数据收集 → 训练 → 评估 → 部署 → 监控 → 重新训练。客户获取属于营销或业务职能，不是构建或运营 ML 系统的技术阶段。其余三个选项（A、B、D）都是典型阶段。

**常见错误：**
- 因为模型监控（D）发生在部署“之后”而选择它，忘记了监控正是实现重新训练和漂移检测的基础。
- 将“客户获取”理解为“收集用户反馈”，认为它属于循环，而事实上反馈在监控阶段收集。

**相关资料：** `lessons/mod-101-foundations/03-ml-infrastructure-basics.md`

## 问题 3
**问题：** MLOps 与传统 DevOps 的主要区别是什么？

**答案：** B) MLOps 在代码版本管理之外，还包括数据和模型的版本管理

**解析：**
DevOps 对代码及基础设施进行版本管理。MLOps 增加两个一等产物：数据集和已训练的模型权重。这是因为复现模型需要完全相同的代码、数据及训练配置，而且即使代码不变，模型也可能漂移。CI/CD 流水线（C）同样是 MLOps 的核心，MLOps 也不依赖特定云平台（D）。

**常见错误：**
- 选择 C，因为认为两种 Ops 实践差异很大，以至于 CI/CD 必须被取代；实际上 MLOps 使用 CT（持续训练）扩展 CI/CD。
- 选择 D，因为大多数教程在云平台上运行，从而错误认为 MLOps 仅适用于云端。

**相关资料：** `lessons/mod-101-foundations/03-ml-infrastructure-basics.md`

## 问题 4
**问题：** 简答题：解释为什么生产 ML 系统需要重新训练模型。

**答案：** 模型性能随时间退化，原因包括：（1）数据漂移——输入特征的分布变化（例如用户行为变化、新商品类别出现）；（2）概念漂移——输入与目标变量之间的关系变化（例如去年用于预测欺诈的信号如今不再有效）。定期使用最新且具有代表性的数据重新训练，可以恢复准确率，使模型与当前现实条件保持一致。

**解析：**
完整答案必须提及两种漂移，或者至少说明“训练完成后世界仍在变化”的一般概念。仅说“为了提高准确率”是不完整的，因为原始测试集上的准确率不会随时间退化，退化的是*新*生产数据上的准确率，这才是重新训练的动机。

**常见错误：**
- 回答“让模型随时间更准确”，将重新训练与在同一数据集上增加训练轮次混淆。
- 忘记区分数据漂移和概念漂移，或将漂移视为单一、不加区分的概念。

**相关资料：** `lessons/mod-101-foundations/03-ml-infrastructure-basics.md`

**答案：** B) 10.7 万–23 万美元

## 问题 6
**问题：** PyTorch 和 TensorFlow 的计算图有什么主要区别？

**答案：** B) PyTorch 使用动态图，TensorFlow 传统上使用静态图

**解析：**
PyTorch 随 Python 执行即时构建计算图（运行时定义），使调试与动态控制流更加自然。TensorFlow 1.x 要求先定义静态图，再在 Session 中运行；TF 2.x 增加了即时执行以匹配 PyTorch 的易用性，但历史与架构上的区别仍然影响许多设计选择。

**常见错误：**
- 颠倒两者并选择 A：这是很常见的混淆，因为 Tensor 一词似乎更具“流动性”和“动态性”。
- 选择 C，因为 TF 2.x 的即时模式与 PyTorch 相似，却忽视了底层图设计理念仍有差异（TF 可以使用 `@tf.function` 编译成静态图）。

**相关资料：** `lessons/mod-101-foundations/04-ml-frameworks.md`

## 问题 7
**问题：** 在生产环境中，推荐使用哪种方法保存 PyTorch 模型？

**答案：** B) `torch.save(model.state_dict(), 'model.pth')`——保存状态字典

**解析：**
仅保存 `state_dict`（张量权重）可将权重与 Python 类定义解耦，使文件大小大致减半，并允许将相同权重加载到重构或派生后的模型中。保存整个模型对象（A）会通过 pickle 序列化类路径，因此任何重命名或重构都可能破坏加载。手动复制文件（C）及原始 pickle（D）不安全且不可移植。

**常见错误：**
- 因为看起来更简单而选择 A，直到模型类移动到不同模块，`torch.load` 因导入错误而失败。
- 因为“PyTorch 底层使用 pickle”而选择 D。这是事实，但原始 pickle 绕过了 PyTorch 针对张量的序列化及安全检查。

**相关资料：** `lessons/mod-101-foundations/04-ml-frameworks.md`

## 问题 8
**问题：** 为什么在 PyTorch 推理之前调用 `model.eval()` 至关重要？

**答案：** B) 它改变 Dropout 和 BatchNorm 等层的行为

**解析：**
`model.eval()` 调用会切换 Dropout、BatchNorm（及其他少数层）所检查的内部 `training` 标志。在评估模式下，Dropout 不再执行丢弃，BatchNorm 使用训练期间学到的运行均值和方差，而非从当前批次重新计算统计量。跳过这一步会产生不确定且不正确的预测，尤其是在批大小较小时。

**常见错误：**
- 选择 A，因为观察到评估模式下的推理有时更快（禁用 Dropout 确实可能如此），却错误认为速度是主要目的。
- 选择 C，因为没有调用时模型“仍然产生输出”；但输出可能悄悄出错，这是最危险的一类缺陷。

**相关资料：** `lessons/mod-101-foundations/04-ml-frameworks.md`

## 问题 9
**问题：** 多选题：以下哪些技术能够优化模型推理？

**答案：** A、B、C、E（量化、TorchScript 编译、批量推理、模型预热）

**解析：**
量化（A）将权重从 FP32 缩减为 INT8，在支持的硬件上可获得约 4 倍的模型体积缩减和 2–4 倍推理加速。TorchScript（B）将 Python 模型编译为图中间表示，带来 10–30% 的加速，并支持不依赖 Python 的部署。批量推理（C）将 GPU Kernel 启动开销分摊到多个请求上。预热（E）提前初始化 JIT 和 CUDA 缓存，避免第一个用户请求比稳态慢 10–100 倍。在训练模式下运行推理（D）是错误的，它保持 Dropout 激活并重新计算 BatchNorm 统计量，同时损害速度和正确性。

**常见错误：**
- 选择 D，因为认为“训练模式做更多工作，因此更全面”；对推理而言恰好相反。
- 遗漏 E（预热），因为它不改变稳态延迟，却忽略用户实际感受到的是冷启动时的 P99 延迟。

**相关资料：** `lessons/mod-101-foundations/04-ml-frameworks.md`, `lessons/mod-101-foundations/06-model-serving-basics.md`

## 问题 10
**问题：** 什么是 ONNX，为什么它有用？

**答案：** B) 用于跨框架部署的通用模型格式

**解析：**
ONNX（Open Neural Network Exchange，开放神经网络交换）定义可移植的计算图格式及共享算子集合，使你可以使用 PyTorch 训练，再使用 TensorFlow、TensorRT 或 ONNX Runtime 提供服务。ONNX Runtime 经过高度优化，通常在相同硬件上优于源框架，因此 ONNX 是生产模型服务的事实标准交换格式。

**常见错误：**
- 选择 A，因为 ONNX 具有 Python 绑定且教程常类似训练代码；但 ONNX 本身是一种*格式*，不是训练器。
- 选择 D，将格式名称与 ResNet 或 Transformer 等架构名称混淆。

**相关资料：** `lessons/mod-101-foundations/04-ml-frameworks.md`

## 问题 11
**问题：** 哪种云服务模式提供对基础设施最多的控制权？

**答案：** C) IaaS（基础设施即服务）

**解析：**
IaaS 暴露底层计算、存储及网络原语（VM、磁盘、VPC），允许选择操作系统、运行时、中间件和应用。随着技术栈上移到 PaaS 再到 SaaS，服务商接管更多层，以控制权换取便利。FaaS（D）位于 PaaS 之上，提供的控制权最少。

**常见错误：**
- 混淆“由服务商管理”（SaaS 的吸引力）和“控制权最多”，二者恰好相反。选择 A（SaaS）颠倒了问题。
- 选择 B（PaaS），因为“平台”听起来会给予平台级控制权，而实际上 PaaS 隐藏了操作系统和运行时层。

## 问题 12
**问题：** 什么是竞价/可抢占实例，何时应该使用？

**答案：** B) 可以在短时间通知后被终止的折扣实例，适合非关键工作负载

**解析：**
云服务商以 60–90% 折扣出售闲置容量，换取在提前 30 秒至 2 分钟通知后收回的权利。它们非常适合容错型工作负载，如批量 ETL、带检查点的分布式训练及 CI Runner，但对于被驱逐就会造成停机的有状态低延迟服务并不安全。

**常见错误：**
- 选择 A，因为“spot”听起来像高级或 VIP 服务；事实上恰好相反，它是最便宜且最不可靠的层级。
- 选择 C，因为部分学习者将竞价实例与计划扩缩容规则混淆。

## 问题 13
**问题：** 多选题：以下哪些属于有效的云成本优化策略？

**答案：** A、B、D、E（合理配置规格、竞价实例、预留实例、自动关闭开发环境）

**解析：**
合理配置规格（A）消除最常见的浪费，即按照峰值负载配置、却只有 5% CPU 利用率的实例。竞价（B）可在可中断工作中节省最高 90%。预留实例或 Savings Plans（D）可对稳定基线工作负载提供 1–3 年承诺下 30–75% 的折扣。夜间和周末自动关闭开发及预发布环境（E）通常可将其账单减半。为“一致性”而让所有内容全天候运行（C），正是促成上述四种正确策略的典型反模式。

**常见错误：**
- 选择 C，因为“始终在线等于可靠”；可靠性来自冗余和自动扩缩容，而非从不关闭资源。
- 遗漏 D，因为“承诺”感觉有风险，却忽视对本来就会运行的工作负载而言，预留容量实际上是可直接获得的节省。

**相关资料：** `lessons/mod-101-foundations/05-cloud-intro.md`

## 问题 16
**问题：** 训练与模型服务工作负载有什么主要区别？

**答案：** B) 训练针对准确率优化，模型服务针对延迟和吞吐量优化

**解析：**
训练是一种批处理任务，在大型数据集上运行数小时或数天，以最终模型准确率评判。模型服务是一种在线系统，在毫秒内响应单个请求，以 P99 延迟、每秒请求数和正常运行时间评判。两者具有不同 SLA、不同的最适硬件配置及扩缩容策略。

**常见错误：**
- 选择 C，因为 GPU 常与训练关联，却忽视延迟敏感的模型服务也经常使用 GPU（或 Inferentia/TPU 等专用加速器）。
- 选择 A，颠倒了方向：训练在每个样本上是两者中更慢的一方。

**相关资料：** `lessons/mod-101-foundations/06-model-serving-basics.md`

## 问题 17
**问题：** 什么是批量推理，它有什么好处？

**答案：** B) 将多个推理请求一起处理；提高 GPU 利用率与吞吐量

**解析：**
GPU 具有大规模并行能力，逐个请求运行会让大多数核心空闲。动态批处理收集 N 个并发请求，将它们作为单个张量输入模型，再拆分输出，以少量排队延迟为代价实现 3–10 倍的吞吐量提升。因此几乎所有生产模型服务栈（Triton、vLLM、TGI）都有批处理器。

**常见错误：**
- 选择 A，将批量*推理*与批量*训练*（并行训练多个模型）混淆。
- 选择 C，将批处理与 A/B 模型版本路由混淆，后者是服务层流量拆分问题。

**相关资料：** `lessons/mod-101-foundations/06-model-serving-basics.md`

## 问题 18
**问题：** 在蓝绿部署策略中，切换时会发生什么？

**答案：** B) 流量立即从旧版本切换到新版本

**解析：**
蓝绿部署并行保留两套完整的生产环境。旧环境（蓝）处理全部流量，新环境（绿）则部署并预热。一次路由切换将 100% 流量发送到绿环境；如果出现异常，则切回蓝环境。以切换期间双倍基础设施为代价，实现接近零的回滚时间。

**常见错误：**
- 选择 A：逐步转移流量属于金丝雀部署，而非蓝绿部署。这是模型服务策略题中最常见的混淆。
- 选择 D：描述的是原地重启，违背了保留两套环境的整个目的。

**相关资料：** `lessons/mod-101-foundations/06-model-serving-basics.md`

## 问题 19
**问题：** 简答题：解释为何在处理生产流量前需要模型预热。

**答案：** 进程启动后的首次推理通常比稳态慢 10–100 倍，因为框架必须 JIT 编译 Kernel、初始化 CUDA 上下文以及 cuDNN/cuBLAS 句柄、分配并调入 GPU 内存，以及从磁盘将权重加载到设备内存。启动时运行几次模拟推理，迫使这些惰性初始化在真实用户访问端点前完成，使生产请求从第一次调用起就获得稳定低延迟。

**解析：**
优秀答案应同时提到原因（JIT、CUDA、内存初始化）和后果（冷启动 P99 延迟尖峰）。没有预热，每次容器重启、自动扩缩容或部署都会让最先到达的真实用户经历数秒延迟；即使平均值看起来正常，这也会主导 P99 指标及 SLO 违规。

**常见错误：**
- 只说“让它更快”，而未解释稳态速度不变；预热专门解决首次请求的问题。
- 忘记提及自动扩缩容与重启的影响，忽视预热对任何弹性部署都十分关键，而不仅限于初次启动。

**相关资料：** `lessons/mod-101-foundations/06-model-serving-basics.md`

## 问题 20
**问题：** 哪种部署策略允许使用真实流量测试新模型，同时不影响用户？

**答案：** C) 影子部署（Shadow deployment）

**解析：**
在影子部署（也称 dark launch）中，生产流量被复制并同时发送到当前模型和新候选模型，但仅将当前模型的响应返回给用户。记录候选模型的预测并离线比较，适合在真实输入上验证延迟、资源使用和预测质量，而不会让用户直接承担新模型的输出风险。金丝雀（B）和蓝绿（A）都会让至少一部分真实用户接触新模型。

**常见错误：**
- 选择 B（金丝雀），因为它是最熟悉的安全策略，却忽略金丝雀仍会将少量真实用户路由到新模型。
- 选择 A（蓝绿），因为两个环境同时存在，却忘记蓝绿一次性切换全部流量，而非镜像流量。

**相关资料：** `lessons/mod-101-foundations/06-model-serving-basics.md`

## 问题 21
**问题：** Docker 多阶段构建的主要好处是什么？

**答案：** B) 排除构建依赖，从而减小最终镜像大小

**解析：**
多阶段 Dockerfile 使用一个具有完整工具链（编译器、开发头文件、构建缓存）的阶段，以及第二个精简阶段，仅通过 `COPY --from=builder` 复制编译后的产物。最终镜像不包含 gcc、build-essential、pip 缓存或源码树，通常从 2 GB 缩小到数百 MB。较小的镜像意味着更快拉取、更小攻击面及更低注册中心成本。

**常见错误：**
- 选择 A，因为“更多阶段等于更快”听起来直观；实际上多阶段构建关注的是层的组成，而非并行性。
- 选择 C，将“多个阶段”与“使用多个基础镜像进行隔离”混淆；安全收益源自更小的攻击面，而非基础镜像多样性。

**相关资料：** `lessons/mod-101-foundations/07-docker-basics.md`

## 问题 22
**问题：** 为什么应该以非 root 用户身份运行容器？

**答案：** B) 这是减小容器逃逸潜在危害的安全最佳实践

**解析：**
容器共享宿主机内核；内核漏洞或错误配置的挂载可能让容器内进程访问宿主机。如果该进程在容器内是 root，默认情况下会映射为宿主机上的 UID 0（除非启用了用户命名空间重映射），因此逃逸会带来 root 级别的破坏能力。使用专用非 root UID 运行可以将影响范围限制为该低权限用户能够执行的操作。

**常见错误：**
- 选择 D，因为 Docker 可以以 rootless 模式运行，但它并不要求容器内使用非 root 用户；这是加固建议，而非强制要求。
- 选择 A，依据“非 root 更轻量”的模糊直觉，这与性能无关。

**相关资料：** `lessons/mod-101-foundations/07-docker-basics.md`

## 问题 23
**问题：** 多选题：哪些 Dockerfile 指令影响层缓存？

**答案：** B、C、E（RUN、COPY、ENV）

**解析：**
原文说明：`RUN`、`COPY`、`ADD`、`ENV` 都会参与构建缓存，缓存键取决于指令文本及涉及的文件。变更复制的文件会使 `COPY` 之后的所有层失效；变更 `ENV` 会使其后引用该环境变量的 `RUN` 缓存失效。`FROM` 选择基础镜像层，但不以相同方式创建你自己的缓存层；`CMD`/`ENTRYPOINT` 仅设置元数据，不构建文件系统层。需注意，元数据指令并不创建新的文件系统层，且基础镜像变化也可能使后续构建缓存失效。

**常见错误：**
- 选择 A（FROM），因为它确实拉取镜像层，但这些是基础镜像层，而非你自身构建所创建的层；原题答案将它视为不直接属于自身缓存逻辑。
- 选择 D（CMD），假设所有“改变容器”的指令都必须影响缓存；CMD 主要更新镜像元数据。

**相关资料：** `lessons/mod-101-foundations/07-docker-basics.md`

## 问题 24
**问题：** Dockerfile 中 `CMD` 与 `ENTRYPOINT` 有什么区别？

**答案：** B) CMD 提供可覆盖的默认参数；ENTRYPOINT 设置主命令

**解析：**
`ENTRYPOINT` 定义容器启动时运行的可执行程序。`CMD` 提供默认参数（若没有 ENTRYPOINT，则提供默认命令），用户可以通过 `docker run image <args>` 覆盖它。惯用组合为 `ENTRYPOINT ["python"]` 加 `CMD ["app.py"]`，默认运行 `python app.py`，但若在 CLI 传入 `other.py`，则运行 `python other.py`。

**常见错误：**
- 选择 A，因为教程总是展示 `CMD`，从而假设它是必须的；两者都不是严格必需，但至少需要某个可运行命令，否则容器没有程序可执行。
- 选择 D，虚构构建时与运行时的区别；两个指令都在容器运行时发挥作用。

**相关资料：** `lessons/mod-101-foundations/07-docker-basics.md`

## 问题 25
**问题：** 如何在 Docker 容器中启用 GPU 访问？

**答案：** B) 安装 NVIDIA Container Toolkit，并使用 --gpus 参数

**解析：**
NVIDIA Container Toolkit 安装一个运行时钩子，在传入 `--gpus all`（或 `--gpus '"device=0,1"'`）时，将宿主机的 NVIDIA 驱动库与 `/dev/nvidia*` 设备节点挂载到容器中。容器自身只需要 CUDA 用户空间库（通常使用 `nvidia/cuda` 基础镜像提供）；内核驱动始终位于宿主机。

**常见错误：**
- 选择 A，因为认为容器像“开箱即用的 VM”；默认情况下它们没有任何 GPU 访问权限。
- 选择 D，尝试手动挂载 `/dev`，这会跳过 Container Toolkit 自动处理的驱动库挂载，通常导致 CUDA 初始化错误。

**问题：** 为什么 FastAPI 特别适合 ML 模型服务？

## 问题 27
**问题：** Pydantic 在 FastAPI 应用中提供什么功能？

**答案：** B) 基于 Python 类型的自动请求和响应验证

## 问题 28
**问题：** 简答题：HTTP 400 和 500 状态码有何区别？何时使用各自的状态码？

**答案：** 4xx 表示客户端错误，即请求本身无效；400 特指请求格式有误或包含无效数据（缺失字段、类型错误、验证失败）。5xx 表示服务端错误，即服务端未能处理请求；500 是通用的“意外异常”状态码，用于未捕获异常、数据库故障或下游服务中断。实践中，调用者必须修正请求后才能重试时使用 400（或 422）；调用者没有做错、服务器恢复后重试可能成功时，使用 500。

**解析：**
优秀答案应明确区分客户端与服务端，并为各自提供具体触发条件。仅说“400 是 Bad Request、500 是 Server Error”却不解释由谁负责修复问题，是较弱的答案；这恰恰是区分二者的运维意义所在。

**常见错误：**
- 验证错误时返回 500：这会误导调用者重复提交相同的无效请求，并污染服务端错误仪表盘和告警。
- 下游服务故障时返回 400，导致依据 5xx 错误率的监控系统无法发现真实故障。

**相关资料：** `lessons/mod-101-foundations/08-api-development.md`

## 问题 30
**问题：** 以下哪项是生产 API 设计的最佳实践？

**答案：** B) 使用通用错误消息，并在服务端记录详细错误

**解析：**
向调用者返回堆栈追踪、SQL 错误、文件路径或库版本，会给攻击者提供免费的侦察工具，还经常通过连接字符串或环境转储泄漏密钥。正确模式是向客户端返回稳定、通用的错误码或消息（例如 `{"error": "internal_error", "request_id": "abc123"}`），同时在服务端记录完整异常、堆栈追踪与上下文，通过请求 ID 关联。

**常见错误：**
- 选择 A，因为“更多信息更便于调试”；对于内部工具是对的，但对于公共 API 很危险。
- 选择 D，将日志记录视为性能成本；结构化异步日志开销很小，而且对于生产调试不可或缺。

**相关资料：** `lessons/mod-101-foundations/08-api-development.md`
