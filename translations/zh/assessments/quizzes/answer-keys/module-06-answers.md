## 问题 1
**问题：** MLOps 的主要目的是什么？

**答案：** B) 自动化并简化从开发到生产的 ML 生命周期

**解析：**
MLOps 将 DevOps 原则应用于机器学习，提供使模型可靠地从 Notebook 进入生产环境并在生产中保持健康的实践、工具和文化。它涵盖数据版本管理、训练、验证、部署、监控和治理，使团队能够更快迭代并减少回归。目标是提高 ML 系统的可靠性与迭代速度，而非提高某个模型的单项评分。

**常见错误：**
- 选择 A（“取代数据科学家”）误解了 MLOps：它通过减少手动部署和监控的重复劳动来增强数据科学家的能力，而不是取代其判断。
- 选择 C（“使模型更准确”）混淆了 MLOps（运维学科）与建模研究；准确率的提升来自数据和建模工作，而非 MLOps 本身。

**相关资料：** lessons/mod-106-mlops/01-introduction-to-mlops.md

## 问题 2
**问题：** 以下哪项不属于 MLOps 生命周期的核心组成部分？

**答案：** C) 前端开发

**解析：**
MLOps 生命周期涵盖数据管理（包括版本管理）、模型开发与训练、评估、部署及持续监控。前端开发可能使用模型预测结果，但不属于 MLOps 学科本身。数据版本管理、模型训练和模型监控都是典型阶段。

**常见错误：**
- 选择 A（“数据版本管理”）忽视了可复现性以及数据版本管理是 MLOps 的基础能力。
- 选择 D（“模型监控”）忽视了对生产环境中的漂移和性能回归进行监控，是 MLOps 最具特色的阶段之一。

## 问题 3
**问题：** 判断题：MLflow 等实验追踪工具只能存储模型训练指标，无法存储模型文件等产物。

**答案：** 错误

**解析：**
MLflow Tracking 记录参数、指标、标签和任意产物，包括序列化模型、图表、数据集及配置文件。MLflow Models 组件还标准化了打包格式，使已记录的模型可以重新加载和部署。将 MLflow 局限为“仅记录指标”，忽略了对可复现性至关重要的产物存储。

**常见错误：**
- 回答正确意味着认为追踪服务器是只写的指标数据库；实际上，`mlflow.log_artifact` 和特定 flavor 的 `log_model` 调用会将文件与 Run 一同持久化。

**相关资料：** lessons/mod-106-mlops/02-mlflow-experiment-tracking.md

## 问题 4
**问题：** 在 MLflow 中，Run 的用途是什么？

**答案：** B) 表示模型训练代码的一次执行

**解析：**
Run 是 MLflow Tracking 中的执行单位，即一次训练（或评估）代码调用，在所属 Experiment 下记录参数、指标、标签和产物。Run 使单次训练任务具有可比性与可复现性。同一 Experiment 下的多个 Run 可并排比较超参数搜索或代码变更。

**常见错误：**
- 选择 A（“执行已部署模型”）混淆了追踪与服务；生产推理由 MLflow Models / Serving 处理，而非 Tracking Run。
- 选择 D（“对代码进行版本控制”）将 Git/DVC 的职责错误归给 MLflow；Run 可以记录 Git commit，但不能取代源代码版本控制。

**相关资料：** lessons/mod-106-mlops/02-mlflow-experiment-tracking.md

## 问题 5
**问题：** ML 实验期间应记录哪些信息？（多选）

**答案：** E) 以上全部（超参数、评估指标、训练时长、数据集版本）

**解析：**
可复现性和有意义的比较要求记录输入（超参数、数据集版本）、输出（评估指标）以及执行上下文（训练时长、硬件、代码 commit）。遗漏任一项都会使人难以解释某次运行为何胜出，或在之后复现它。与无法调试的模型相比，记录成本微不足道。

**常见错误：**
- 仅选择 A 和 B，遗漏数据集版本，是常见错误；没有数据集版本管理，无法判断指标变化源自代码还是数据。
- 遗漏训练时长会忽略生产规划所需的资源与成本信号。

**相关资料：** lessons/mod-106-mlops/02-mlflow-experiment-tracking.md

## 问题 6
**问题：** MLflow 中实验标签的目的是什么？

**答案：** A) 组织与筛选实验

**解析：**
标签是附加到 Run 或 Experiment 的任意键值元数据（如 `team=ranking`、`dataset=v3`、`purpose=baseline`），允许你通过 UI 或 API 搜索、分组及筛选。它们仅用于组织元数据，不影响模型行为或部署。

**常见错误：**
- 选择 B（“提高模型准确率”）将元数据标签与训练输入混淆，标签不会输入模型。
- 选择 D（“自动部署模型”）将标签与模型注册表的阶段转换混淆，后者才是与部署相关的标记。

**相关资料：** lessons/mod-106-mlops/02-mlflow-experiment-tracking.md

## 问题 7
**问题：** 简答题：解释在 MLflow 中记录参数与记录指标的区别。

**答案：** 参数是输入配置值（如学习率、批大小、模型类型），通常在 Run 开始时通过 `mlflow.log_param` 记录一次。指标是测量得到的输出值（如准确率、损失、F1），通过 `mlflow.log_metric` 记录，可以使用 step 索引反复记录，形成可按训练轮次绘制的时间序列。

**解析：**
这一区分非常重要，因为参数描述实验设置，而指标描述实验结果。Run 中的参数一旦设置便不可变；指标是仅追加的序列。混淆二者会使 Run 难以比较，并破坏依赖标量参数和时间序列指标的工具。

**常见错误：**
- 认为两者“只是数值”，忽视了指标的时间序列性质和参数的配置作用。
- 忘记指标支持 `step` 参数，导致覆盖数值而不是构建训练曲线。

**相关资料：** lessons/mod-106-mlops/02-mlflow-experiment-tracking.md

## 问题 8
**问题：** 特征存储解决什么问题？

**答案：** D) 以上全部（训练与服务偏差、跨团队特征复用、时间点正确性）

**解析：**
特征存储集中管理特征定义和计算，使训练与服务使用相同逻辑生成特征，消除偏差。它们将特征作为共享目录公开，让多个团队发现并复用特征。构建历史训练集时，还通过时间点连接防止标签泄漏。

**常见错误：**
- 仅选择 A（训练与服务偏差）忽视了复用和时间点正确性，这两者也是特征存储存在的重要理由。
- 仅选择 C 忽视了防止训练与服务偏差可以说是其最核心的价值主张。

**相关资料：** lessons/mod-106-mlops/04-feature-stores-engineering.md

## 问题 9
**问题：** 离线特征存储与在线特征存储有何区别？

**答案：** D) 以上全部（离线用于训练、在线用于推理；离线较慢、在线较快；离线保存历史数据、在线保存近期最新值）

**解析：**
离线存储（如 BigQuery、Snowflake 等数据仓库，或对象存储上的 Parquet）保存完整的特征历史，用于训练和回填，优先优化吞吐量而非延迟。在线存储（如 Redis、DynamoDB、Cassandra）以实体 ID 为键保存最新特征值，用于实时推理中的低延迟查询。特征存储同步二者，使同一个逻辑特征能够以两种形态提供。

**常见错误：**
- 仅选择 A（训练与推理）在技术上正确，但忽略了决定存储选型的延迟和数据形态差异。
- 仅选择 B（慢与快）忽略了各存储层保留的数据类型同样重要。

**相关资料：** lessons/mod-106-mlops/04-feature-stores-engineering.md

## 问题 10
**问题：** 判断题：特征存储自动保证训练时使用的特征与生产服务时使用的特征一致。

**答案：** 正确

**解析：**
因为特征定义与转换逻辑集中在一个位置，并物化到离线和在线存储，所以同一代码路径为训练和服务生成特征值。这是特征存储消除训练与服务偏差的结构性机制，也是采用特征存储的核心保障。

**常见错误：**
- 回答错误通常源于混淆上游数据质量问题导致的偏差（仍有可能发生）与定义层面的偏差（特征存储消除的偏差）。

**相关资料：** lessons/mod-106-mlops/04-feature-stores-engineering.md

## 问题 11
**问题：** 在 Feast 中，什么是 Feature View？

**答案：** B) 一组具有共同数据源的相关特征的定义

**解析：**
Feast 中的 `FeatureView` 声明源自单一数据源的一组逻辑特征，关联一个或多个实体，并具有 TTL 与 Schema。它是 Feast 向在线存储物化数据以及为训练数据执行时间点连接的单位。Feature View 是定义，而非 UI 或缓存。

**常见错误：**
- 选择 A（“用于查看特征的 UI”）混淆了配置对象与可视化界面。
- 选择 D（“常用特征的缓存”）混淆了 Feature View 与在线存储，后者才是真正的低延迟缓存。

**相关资料：** lessons/mod-106-mlops/04-feature-stores-engineering.md

## 问题 12
**问题：** 面向 ML 的 CI/CD 与传统软件 CI/CD 有何不同？

**答案：** D) 以上全部（包含数据验证；测试模型性能而不仅是代码正确性；除代码外还对数据及模型进行版本管理）

**解析：**
ML 流水线不仅可能因代码缺陷失败，还可能因数据质量回归失败，因此验证必须扩展到 Schema 与分布检查。测试必须验证模型在留出数据及各数据切片上的行为，而不仅对代码路径进行单元测试。可复现性则需要将代码、数据和模型产物三者一同进行版本管理。

**常见错误：**
- 仅选择 A 忽略了“模型本身现在是构建产物的一部分”这一更深层的差异。
- 仅选择 C 忽略了真正需要测试的对象（数据与模型行为）才是 ML CI/CD 的特色。

**相关资料：** lessons/mod-106-mlops/05-cicd-ml-models.md

## 问题 13
**问题：** 自动化 ML 测试应包括哪些内容？（多选）

**答案：** E) 以上全部（数据 Schema 验证、模型性能阈值、推理延迟检查、模型公平性测试）

**解析：**
完整的 ML 测试套件检查输入（Schema 与分布）、输出（准确率、精确率、召回率阈值及切片指标）、运行时特性（延迟和吞吐量 SLO），以及负责任 AI 的属性（跨人口群体切片的公平性）。遗漏任一项都将产生一类无法在生产部署前捕获的缺陷。这些检查均应在部署流水线中自动运行。

**常见错误：**
- 仅选择 A 和 B，认为 ML 测试只是增强版单元测试，忘记了延迟等非功能性需求。
- 遗漏公平性测试是常见疏忽，往往直到生产用户投诉才暴露。

**相关资料：** lessons/mod-106-mlops/05-cicd-ml-models.md

## 问题 14
**问题：** 在 ML 模型的部署门禁中，哪些标准可能阻止模型部署？

**答案：** D) 以上全部（与当前生产模型相比性能回归、超过延迟阈值、公平性检查失败）

**解析：**
部署门禁从质量（无指标回归）、服务（延迟、吞吐量符合 SLO）与责任（公平性、偏差）等维度，将候选模型与当前生产冠军模型进行比较。任何单项失败都应阻止晋升，以保障生产安全。门禁是发布检查清单的自动化版本。

**常见错误：**
- 仅选择 A，将部署门禁视为单纯的准确率门禁，忽略服务和伦理约束。
- 仅选择 B，将门禁视为性能测试，遗漏模型质量及公平性维度。

**相关资料：** lessons/mod-106-mlops/05-cicd-ml-models.md

## 问题 15
**问题：** 简答题：解释什么是“金丝雀部署”，以及为什么它对 ML 模型有用。

**答案：** 金丝雀部署将少量真实流量（通常为 1–10%）路由到新模型版本，大部分流量继续访问现有版本。你在真实生产流量中监控金丝雀版本的业务与运维指标，然后逐步提高流量比例，或在出现回归时快速回滚。对 ML 模型尤其有价值，因为离线指标经常与真实用户行为不一致；金丝雀流量暴露是验证离线分数的提升确实有益于生产环境的最低成本方式。

**解析：**
金丝雀部署限制坏模型的影响范围：在 5% 流量下，即使灾难性回归也只影响发布窗口内 5% 的用户。它还产生无法从预发布环境获取的真实信号，例如延迟、错误率和业务 KPI。结合护栏指标越界时的自动回滚，ML 模型可以安全地频繁发布。

**常见错误：**
- 将金丝雀与蓝绿部署混淆（后者从 0% 直接切换到 100%，没有逐步提升流量）。
- 遗漏回滚部分；没有监控和回滚的金丝雀部署只不过是缓慢部署。

**相关资料：** lessons/mod-106-mlops/06-model-deployment-strategies.md

## 问题 16
**问题：** 对于不需要立即获得结果的大型数据集预测，哪种部署模式最佳？

**答案：** B) 批量推理

**解析：**
批量推理按照计划（例如每晚）对大型数据集运行模型，将预测结果写入存储，并以异步方式消费。它最大化吞吐量和每次预测的硬件利用率，当预测延迟可以是数小时而非毫秒时，这是正确选择。示例包括每晚刷新推荐结果、潜在客户评分或客户流失风险评估。

**常见错误：**
- 选择 A（实时服务）：没有逐请求延迟要求时会浪费基础设施。
- 选择 C（流处理）：适合持续事件流，而非无紧迫性的大批数据评分。

**相关资料：** lessons/mod-106-mlops/06-model-deployment-strategies.md

## 问题 17
**问题：** 模型量化的主要好处是什么？

**答案：** B) 减小模型体积并提高推理速度

**解析：**
量化将模型权重和/或激活值从高精度浮点数（FP32）转换为低精度表示（FP16、INT8，有时是 INT4）。结果是更小的产物、更低的内存带宽需求，以及在支持低精度的硬件上更快的矩阵乘法。准确率通常略有下降，这是权衡而非目标。

**常见错误：**
- 选择 A（“提高准确率”）颠倒了权衡关系；量化通常牺牲少量准确率，以换取体积和速度优势。
- 选择 C（“更容易训练”）将训练后量化与训练优化混淆；量化主要是推理阶段技术。

**相关资料：** lessons/mod-106-mlops/06-model-deployment-strategies.md

## 问题 18
**问题：** 判断题：Kubernetes 的 HPA 可以根据 CPU、内存以及请求速率等自定义指标自动扩缩容 ML 模型服务 Pod。

**答案：** 正确

**解析：**
HPA 根据观测指标调整 Pod 副本数量。它开箱即用地支持 CPU 和内存；通过 `external` 与 `custom` 指标 API（通常由 Prometheus Adapter 或 KEDA 支持），还可以根据 RPS、队列深度、GPU 利用率或任何自定义信号扩缩容。这使 HPA 适合突发性的推理工作负载。

**常见错误：**
- 回答错误通常源于认为 HPA 只支持 CPU；自定义指标 API 已正式可用多个版本。

## 问题 19
**问题：** 在高吞吐量场景中，哪种模型服务协议通常更快？

**答案：** B) gRPC

**解析：**
gRPC 使用 HTTP/2 与二进制 Protocol Buffers，支持在单个连接上复用多个流，并避免 JSON 序列化开销。对于高吞吐量、低延迟模型服务，尤其是内部服务间流量，它通常优于 REST/JSON。主流模型服务端（Triton、TF Serving、TorchServe、KServe）也因此提供 gRPC 端点。

**常见错误：**
- 选择 A（REST）混淆了普及程度、易于调试与原始性能；REST/JSON 具有更高的序列化开销。
- 选择 D（WebSockets）：适合双向流式 UI，但不是标准的高吞吐量推理协议。

**相关资料：** lessons/mod-106-mlops/06-model-deployment-strategies.md

## 问题 20
**问题：** 在运行 A/B 测试之前计算样本量的目的是什么？

**答案：** D) 以上全部（确定运行时长、确保检测最小效应的统计功效、避免运行时间超过必要长度）

**解析：**
在已知基线指标、最小可检测效应、显著性水平和目标统计功效的情况下，样本量计算告诉你需要多少用户（以及大致多少天）才能得到有意义的结果。缺少这一步，测试可能因统计功效不足而错过真实效应，也可能运行过久并浪费机会成本。这是可信实验的先决条件。

**常见错误：**
- 仅选择 A，将样本量计算视为排期工作，忘记了统计功效这一半。
- 仅选择 C，将其视为成本优化，忽略低功效测试带来的假阴性风险。

## 问题 21
**问题：** 什么是“样本比例失配”（SRM），为什么值得关注？

**答案：** D) 以上全部（观测到的分流比例偏离预期比例、可能表明分配或日志记录存在缺陷、可能使结果失效）

**解析：**
SRM 通常使用卡方检验（p < 0.001）检测各变体实际用户分流比例是否显著偏离预期比例（例如样本量 N 很大时，配置为 50/50，但实际为 49.2/50.8）。常见根因包括分桶缺陷、存在偏差的曝光日志、两组不均匀的机器人过滤，或导致用户流失的重定向。由于总体不再具有可比性，受 SRM 影响的实验中任何处理效应估计都值得怀疑，应在相信结果前停止测试并调查。

**常见错误：**
- 仅选择 A 描述了症状，但没有解释从业者为何非常关注它。
- 仅选择 C 将 SRM 视为结果问题，而非通常具有可修复根因的观测埋点问题。

**相关资料：** lessons/mod-106-mlops/07-ab-testing-experimentation.md

## 问题 22
**问题：** 判断题：在 A/B 测试中，做出部署决策前总是应等待达到统计显著性。

**答案：** 错误

**解析：**
“总是等到 p<0.05”在多个方面都不正确。序贯检验方法（mSPRT、组序贯检验、贝叶斯后验）允许有效的提前停止。即使主要指标尚不显著，护栏指标也可能强制停止实验。此外，具有统计显著性的效应仍可能太小而不值得上线（实际显著性与统计显著性的区别），而效应不显著且置信区间紧密围绕零的结果，则可能支持发布中性但成本更低的变体。

**常见错误：**
- 回答正确忽略了护栏指标越界时应立即停止测试，无论主要指标是否显著。
- 这也混淆了统计显著性与是否值得决策；很小的效应可能在统计上真实存在，却没有实际意义。

**相关资料：** lessons/mod-106-mlops/07-ab-testing-experimentation.md

## 问题 23
**问题：** A/B 测试中的护栏指标是什么？

**答案：** A) 不得退化超过阈值的指标

**解析：**
护栏指标防止发布在主要指标上获胜、却损害其他重要事项（延迟、错误率、收入、留存、公平性）的处理方案。只有主要指标改善且没有护栏指标越过可接受的退化阈值时，才应发布测试变体。护栏指标编码了“获胜”必须遵守的约束。

**常见错误：**
- 选择 B（“主要成功指标”）混淆了护栏与优化目标；两者恰好相反，护栏是约束而非目标。
- 选择 D（“流量分配指标”）混淆了护栏与分桶或分流逻辑，二者无关。

## 问题 24
**问题：** 模型卡（Model Card）的用途是什么？

**答案：** A) 记录模型细节、预期用途及局限性

**解析：**
模型卡（Mitchell 等，2019）是简短的结构化文档，描述模型的预期用途、训练数据、不同数据切片的评估结果、伦理考量及已知局限。它支持下游用户在知情的情况下使用模型，也越来越多地被治理框架和监管机构要求。模型卡属于文档，而非遥测或工具。

**常见错误：**
- 选择 B（“随时间追踪性能”）混淆了模型卡与生产监控仪表盘。
- 选择 D（“对模型进行版本控制”）混淆了模型卡与模型注册表，后者负责版本管理和阶段转换。

## 问题 25
**问题：** 简答题：列出三种 ML 特有的技术债务，并分别提供一个简短示例。

**答案：** Sculley 等人的《Hidden Technical Debt in Machine Learning Systems》（机器学习系统中的隐性技术债务）中的三类常见债务：

1. **数据债务**：不稳定或缺少文档的输入流水线。示例：生产模型消费的某个特征由其他团队的 ETL 每晚悄悄重建，且没有 Schema 契约，导致上游 Schema 变化时推理中断。
2. **模型债务**：相互纠缠或重复的模型。示例：三个团队分别使用重叠的特征发布自己的流失预测模型，且都没有文档；重新训练其中一个模型会改变下游联合分布（CACE 原则：“改变任何一件事都会改变所有事情”）。
3. **监控债务**：模型行为缺乏可观测性。示例：推荐系统的 CTR 已悄然下降六周，因为没有漂移检测器或性能仪表盘，团队直到产品经理告知才知道。

其他可接受示例包括胶水代码或流水线丛林债务、配置债务（大量未经测试的超参数配置）、反馈循环债务（模型输出成为下一轮训练输入），以及可复现性债务（训练数据集或环境丢失）。

**解析：**
ML 系统积累债务的方式与传统软件不同，因为模型行为依赖数据，且现实世界也在变化。明确债务类别有助于团队确定优先级：数据和监控债务通常比模型债务具有更大的影响范围，因为它们会导致静默故障。经典参考资料是 Sculley 等人的 NeurIPS 论文。

**常见错误：**
- 仅列出通用软件债务（例如“未经测试的代码”），却没有 ML 特有的背景，未抓住题目重点。
- 仅提及类别而没有具体示例会损失评分，因为评分标准明确为示例分配分数。

**相关资料：** lessons/mod-106-mlops/08-best-practices-governance.md
