## 问题 1
**问题：** LLM 基础设施与传统 ML 基础设施的主要区别是什么？

**答案：** B) LLM 需要大量 GPU 显存和专门的模型服务优化

**解析：**
LLM 通常具有 7B 到 70B 以上的参数，这意味着需要专门的 GPU 基础设施以及 PagedAttention、KV Cache 管理、连续批处理等内存优化手段。传统 ML 模型（随机森林、小型神经网络）很少受到这些限制，因此其服务技术栈存在根本差异。

**常见错误：**
- 选择 A：由于内存带宽要求，生产推理中的 LLM 几乎不会在 CPU 上运行。
- 选择 D：云端托管 LLM 极为常见；本地部署只是选项之一，并非定义性特征。

**相关资料：** lessons/mod-110-llm-infrastructure/01-introduction-llm-infrastructure.md

## 问题 2
**问题：** 对于低流量 LLM 应用，哪种部署模式最具成本效益？

**答案：** B) 支持自动缩容至零的无服务器推理

**解析：**
低流量工作负载大部分时间处于空闲状态，因此仅在请求到达时按秒付费是成本最低的模式。缩容至零模式（如 SageMaker Serverless、Modal、RunPod Serverless）避免了 GPU 始终运行产生的浪费。

**常见错误：**
- 选择 A：专用全天候 GPU 集群使空闲成本最大化，与零星流量的成本效益目标相反。
- 选择 D：仅使用 CPU 的推理速度过慢，即使每小时价格便宜，单位经济效益也很差。

**相关资料：** lessons/mod-110-llm-infrastructure/01-introduction-llm-infrastructure.md

## 问题 3
**问题：** 使用 FP16 精度提供 7B 参数 LLM 服务时，典型的 GPU 显存需求是多少？

**答案：** C) 14–16 GB

**解析：**
FP16 每个参数占 2 字节，因此仅权重就需要 7B × 2 字节 ≈ 14 GB。再加上 KV Cache、激活值和框架开销，就达到 14–16 GB。这也是 T4（16 GB）显存勉强够用而 A10G（24 GB）较为宽裕的原因。

**常见错误：**
- 选择 B（7–10 GB）：混淆了参数数量（7B）与字节数量；FP16 需要两倍的存储空间。
- 选择 D（40 GB 以上）：该数值适用于更大的模型，例如 FP16 的 30B 以上模型或未量化的 70B 模型。

**相关资料：** lessons/mod-110-llm-infrastructure/01-introduction-llm-infrastructure.md

## 问题 4
**问题：** 哪个因素对 LLM 推理延迟的影响最大？

**答案：** C) GPU 显存带宽与 KV Cache 管理

**解析：**
自回归解码受内存带宽限制：每生成一个 token，都需要通过 GPU 的内存层次结构读取完整模型权重与 KV Cache。模型加载完成后，CPU、存储 IOPS 和网络很少成为瓶颈。

**常见错误：**
- 选择 A：张量已经位于 GPU 上后，CPU 速度的影响很小。
- 选择 D：存储 IOPS 只影响模型加载过程，而不是每个 token 的延迟。

**相关资料：** lessons/mod-110-llm-infrastructure/01-introduction-llm-infrastructure.md

## 问题 5
**问题：** vLLM 中的 PagedAttention 是什么？

**答案：** B) 使用虚拟内存分页管理 KV Cache 内存的技术

**解析：**
PagedAttention 借鉴操作系统的虚拟内存分页概念，将其应用于 KV Cache 块。它消除碎片、允许序列共享内存块（例如用于前缀缓存），并显著增大批大小，这是 vLLM 实现高吞吐量的核心原因。

**常见错误：**
- 选择 A：PagedAttention 不改变模型大小或权重。
- 选择 D：它是一种内存管理技术，而非 GPU 调度器。

**相关资料：** lessons/mod-110-llm-infrastructure/02-vllm-deployment.md

## 问题 6
**问题：** vLLM 开箱即用地提供哪种 API 兼容性？

**答案：** C) OpenAI API 兼容性

**解析：**
vLLM 提供兼容 OpenAI 的服务端（`/v1/chat/completions`、`/v1/completions`、流式输出），因此现有 OpenAI SDK 客户端只需修改基础 URL，即可指向自托管的 vLLM 端点。

**常见错误：**
- 选择 A：vLLM 不提供 Hugging Face Inference API 接口。
- 选择 D：AWS Bedrock 使用自己的 SigV4 签名 API，vLLM 不模拟该接口。

## 问题 7
**问题：** vLLM 的 `--max-model-len` 参数控制什么？

**答案：** B) 输入与输出的最大上下文长度

**解析：**
`--max-model-len` 限制每条序列的 token 总长度（提示词加生成内容）。它是一个关键的显存预算调节参数，与 `--max-num-seqs` 共同决定批大小与 KV Cache 的占用空间。

**常见错误：**
- 选择 A：模型参数量由检查点确定，而不是由 CLI 参数决定。
- 选择 C：这一作用由 `--max-num-seqs` 承担，而非 `--max-model-len`。

**相关资料：** lessons/mod-110-llm-infrastructure/02-vllm-deployment.md

## 问题 8
**问题：** 在 Kubernetes 上部署 vLLM 时，推荐采用哪种资源请求模式？

**答案：** B) GPU 的 request 和 limit 应相等

**解析：**
Kubernetes 中的 GPU 是独占且不可超额分配的资源。设备插件仅接受 request 和 limit 中的整数数量，因此二者必须相等（例如两处都配置 `nvidia.com/gpu: 1`）。不匹配的值要么无法通过验证，要么其行为等同于二者相等。

**常见错误：**
- 选择 A：标准 NVIDIA 设备插件不支持 GPU 超额分配。
- 选择 C：省略 limits 会引起调度和配额问题，不属于有效的 GPU 配置模式。

**相关资料：** lessons/mod-110-llm-infrastructure/02-vllm-deployment.md

## 问题 9
**问题：** 检索增强生成（RAG）的主要目的是什么？

**答案：** C) 利用外部知识库中的相关上下文增强 LLM 回复

**解析：**
RAG 在推理阶段将检索得到的最新内容或专有内容注入提示词，无须重新训练，即可缓解基础 LLM 的训练数据截止时间和缺少私有数据的问题。

**常见错误：**
- 选择 A：RAG 是推理阶段的模式，不影响训练速度。
- 选择 B：RAG 不会缩小模型，而是在模型周围增加检索系统。

**相关资料：** lessons/mod-110-llm-infrastructure/03-rag-systems.md

## 问题 10
**问题：** 在 RAG 管道中，“分块”（chunking）是什么？

**答案：** B) 将文档划分为更小、具有语义意义的片段

**解析：**
分块将源文档切分成适合检索的单元（通常为 200–1000 token），使其适合嵌入模型的输入窗口，并提供聚焦的上下文。固定大小、感知句子边界和递归分块等策略会直接影响检索质量。

**常见错误：**
- 选择 A：压缩权重是量化，而非分块。
- 选择 D：划分 GPU 工作负载属于分片或张量并行，是完全不同的问题。

**相关资料：** lessons/mod-110-llm-infrastructure/03-rag-systems.md

## 问题 11
**问题：** 高级 RAG 系统中重排序步骤的目的是什么？

**答案：** B) 使用更精细的模型重新排列候选结果，提高检索精确率

**解析：**
双编码器快速检索较广泛的候选集合，然后交叉编码器重排序模型对每个（查询、候选项）组合进行联合评分，实现更准确的相关性排名。结果是上下文窗口前部的精确率显著提高。

**常见错误：**
- 选择 A：字母顺序排序与相关性无关。
- 选择 D：去重是独立的后处理步骤，而非重排序。

**相关资料：** lessons/mod-110-llm-infrastructure/03-rag-systems.md

## 问题 12
**问题：** 嵌入模型的哪个特性对 RAG 检索质量最重要？

**答案：** C) 查询与文档嵌入向量之间的语义相似性

**解析：**
检索质量最终取决于嵌入空间能否将语义相关的查询和文档聚集在一起。MTEB、NDCG 等基准或指标正是对这类质量的度量。质量达到可接受水平后，模型大小和速度才是次要的权衡因素。

**常见错误：**
- 选择 A：大模型并不一定更好；不少小模型在检索基准中排名领先。
- 选择 B：推理速度关系到成本与延迟，而非检索质量。

**相关资料：** lessons/mod-110-llm-infrastructure/03-rag-systems.md

## 问题 13
**问题：** 向量数据库进行相似性搜索时使用的主要数据结构是什么？

**答案：** C) HNSW 或 IVF 等近似最近邻（ANN）索引

**解析：**
对数百万个高维向量进行暴力搜索过慢，因此向量数据库依靠 ANN 结构——HNSW（基于图）、IVF（倒排列表）、PQ（乘积量化）以及它们的组合——实现次线性搜索，并允许调整召回率。

**常见错误：**
- 选择 A：B 树针对一维有序数据设计，而非高维相似性。
- 选择 B：哈希表提供精确查找，而非近似最近邻搜索。

**相关资料：** lessons/mod-110-llm-infrastructure/04-vector-databases.md

## 问题 14
**问题：** 在 Qdrant 中，“collection”（集合）是什么？

**答案：** B) 具有相同维度与配置的一组命名向量

**解析：**
Qdrant 集合是顶层容器，类似于 SQL 表。它为其中所有数据点规定向量维度、距离度量与 HNSW 配置，并保存这些点的 payload 元数据。

**常见错误：**
- 选择 A：用户由集群或认证层管理，而不是作为集合。
- 选择 C：备份是快照，而非集合。

**相关资料：** lessons/mod-110-llm-infrastructure/04-vector-databases.md

## 问题 15
**问题：** 增加 HNSW 的 `ef_construct` 参数会带来什么权衡？

**答案：** A) 准确率更高，但索引构建更慢

**解析：**
`ef_construct` 表示将每个点插入 HNSW 图时探索的候选列表大小。较大的值会构建质量更高的图（搜索时召回率更好），但增加索引构建的 CPU 成本。它不会直接改变查询时的 `ef`。

**常见错误：**
- 选择 B：颠倒了实际的权衡方向。
- 选择 D：“总是增加该值”忽略了真实存在的索引构建时间成本。

**相关资料：** lessons/mod-110-llm-infrastructure/04-vector-databases.md

## 问题 16
**问题：** 对于生产级 RAG 系统，哪项向量数据库功能至关重要？

**答案：** B) 在保持向量搜索性能的同时按元数据过滤

**解析：**
生产级 RAG 需要多租户隔离、权限范围限制、时效性窗口、文档类型过滤等。没有高效的过滤式 ANN 搜索（预过滤或支持过滤的 HNSW），准确率与租户隔离都会受到严重影响。

**常见错误：**
- 选择 A：向量数据库不是 LLM 托管服务，这是推理层的职责。
- 选择 C：向量数据库不负责训练模型。

## 问题 17
**问题：** LoRA（低秩适配）的作用是什么？

**答案：** B) 在冻结的预训练权重上添加可训练的低秩矩阵

**解析：**
LoRA 冻结基础权重 `W`，训练较小的秩为 `r` 的矩阵 `A` 和 `B`，使有效权重变为 `W + BA`。这可将可训练参数量减少约 1000 倍，使单 GPU 微调成为可能，同时保留基础模型能力。

**常见错误：**
- 选择 A：用于推理的压缩属于量化或蒸馏，而非 LoRA。
- 选择 D：LoRA 支持高效微调，但不会自动提高准确率。

**相关资料：** lessons/mod-110-llm-infrastructure/05-llm-fine-tuning-infrastructure.md

## 问题 18
**问题：** QLoRA 相比 LoRA 的主要优势是什么？

**答案：** C) 将基础模型量化为 4 位，同时以更高精度训练 LoRA 适配器

**解析：**
QLoRA 将冻结的基础模型存储为 NF4（4 位），在前向传播时即时反量化，并使 LoRA 适配器保持 BF16 精度。结果是基础模型显存占用约降至四分之一，使 65B 模型能够在 24–48 GB GPU 上微调。

**常见错误：**
- 选择 A：由于反量化开销，QLoRA 每步通常比普通 LoRA 更慢。
- 选择 B：QLoRA 相比 LoRA 并不会天然提高准确率。

**相关资料：** lessons/mod-110-llm-infrastructure/05-llm-fine-tuning-infrastructure.md

## 问题 19
**问题：** 微调 LLM 时，“灾难性遗忘”是什么？

**答案：** B) 模型过拟合微调数据时忘记预训练知识

**解析：**
激进的全量微调使权重过度偏向新数据分布，导致通用预训练能力退化。缓解措施包括 LoRA、降低学习率、使用通用数据的回放缓冲区，以及缩短训练过程。

**常见错误：**
- 选择 A：GPU OOM 是基础设施错误，而非学习现象。
- 选择 C：检查点丢失属于运维问题，与模型行为无关。

**相关资料：** lessons/mod-110-llm-infrastructure/05-llm-fine-tuning-infrastructure.md

## 问题 20
**问题：** 将 LLM 从 FP16 量化为 INT8 会产生什么效果？

**答案：** A) 内存占用减半，质量损失很小

**解析：**
FP16 每个数值使用 16 位，INT8 使用 8 位，因此占用空间恰好减半。现代方案（LLM.int8()、SmoothQuant、GPTQ-8bit）将质量下降控制在低个位数范围，并可在支持的 GPU 上利用 INT8 Tensor Core。

**常见错误：**
- 选择 B（4 倍）：该数值对应 FP16 → INT4，而非 INT8。
- 选择 D：INT8 量化已得到广泛部署，具有实际可用性。

**相关资料：** lessons/mod-110-llm-infrastructure/06-llm-serving-optimization.md

## 问题 21
**问题：** LLM 服务中的“连续批处理”是什么？

**答案：** C) 在其他请求完成时动态将新请求加入批次

**解析：**
连续批处理也称为迭代级调度，在每一步解码时将已完成的序列移出批次，并将新序列补入。它消除了变长生成造成的队首阻塞，是现代 LLM 服务中提升吞吐量最显著的优化之一。

**常见错误：**
- 选择 A：这描述的是流式训练数据，而非服务。
- 选择 B：将相同提示词分批处理属于前缀共享，而非连续批处理。

**相关资料：** lessons/mod-110-llm-infrastructure/06-llm-serving-optimization.md

## 问题 22
**问题：** Flash Attention 旨在优化什么？

**答案：** B) 注意力计算期间的内存访问模式

**解析：**
Flash Attention 是一种 IO 感知的精确注意力算法，在 SRAM 中对 QKV 分块，避免在 HBM 中物化完整的 N×N 注意力矩阵。数学计算结果保持相同，但内存访问流量显著减少，实际运行时间大幅缩短。

**常见错误：**
- 选择 A：Flash Attention 不压缩模型。
- 选择 D：它是单 GPU 内核优化，而非网络技术。

**相关资料：** lessons/mod-110-llm-infrastructure/06-llm-serving-optimization.md

## 问题 23
**问题：** 在多模型 LLM 平台中，模型路由器的作用是什么？

**答案：** B) 根据任务、成本或延迟要求将请求路由至适当模型

**解析：**
模型路由器对每个请求进行分类，并将其分发给合适的模型——简单对话使用小型快速模型，复杂推理使用大型较慢模型，代码任务使用代码专用模型等。它在异构模型集群中平衡质量、延迟和成本。

**常见错误：**
- 选择 A：GPU 负载均衡属于服务网格或副本调度器的职责，而非模型路由器。
- 选择 C：网络层路由属于第 3/4 层网络问题，而非模型平台问题。

**相关资料：** lessons/mod-110-llm-infrastructure/07-llm-platform-architecture.md

## 问题 24
**问题：** 在 LLM 系统中实现语义缓存的主要好处是什么？

**答案：** B) 对相似查询提供缓存回复，从而降低基础设施成本

**解析：**
语义缓存使用嵌入向量的相似性作为匹配依据，而非精确字符串，因此改述后的查询也能命中缓存。对于意图重复的工作负载（常见问题、客服、常用提示词），这通常可以减少 30–70% 的 LLM 调用，直接降低成本和延迟。

**常见错误：**
- 选择 A：缓存有助于降低推理延迟，而不是缩短模型加载时间。
- 选择 C：缓存回复不能提高模型准确率，只是重用先前的输出。

**相关资料：** lessons/mod-110-llm-infrastructure/07-llm-platform-architecture.md

## 问题 25
**问题：** 当 LLM 服务性能下降时，应首先监控什么？

**答案：** B) GPU 利用率、显存和队列深度

**解析：**
LLM 服务受 GPU 资源限制，因此故障初筛的第一步是查看 GPU 资源三角：利用率（计算饱和度）、显存（OOM 和 KV Cache 压力）、队列深度（等待接纳的请求积压）。这些指标可以在数秒内定位容量或工作负载问题。

**常见错误：**
- 选择 A：代码质量指标无法为实时性能下降提供运行时信号。
- 选择 D：对于纯 LLM 推理而言，数据库很少成为瓶颈（RAG 除外）。

**相关资料：** lessons/mod-110-llm-infrastructure/08-production-llm-best-practices.md
