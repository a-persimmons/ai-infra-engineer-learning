# 练习 01：数据管道架构设计

**时长：** 3 小时
**难度：** 入门进阶
**前置条件：** 无

## 目标

针对现实场景设计数据管道架构：推荐系统需要每日训练数据（批处理）和分钟以内的用户事件摄取（流式处理）。不编写任何代码，产出完整设计文档，涵盖摄取、处理、存储、调度、可观测性及故障处理。

## 为什么重要

多数管道故障源于第一行代码编写之前的设计选择。能够编写经得起评审的设计文档的工程师，可以显著降低上线失败率（原文称降低一个数量级）。

## 场景

**产品：** 中型电商网站的首页商品推荐系统。

**数据源：**
- `events.click`、`events.view`、`events.purchase`——用户行为，每天约 1,000 万条。
- `catalog.products`——商品主数据，每日快照，约 50 万行。
- `users.profile`——用户维度，每日快照，约 500 万行。
- `inventory.stock`——需要分钟以内的更新，以便过滤缺货商品。

**输出：**
- 每日训练数据集（`s3://recs/training/<date>/`），用于离线模型重新训练。
- 在线特征存储（Redis）更新，用于特征服务。
- 实时缺货缓存更新（Redis pub/sub）。

**约束：**
- 三名工程师。
- 仅使用 AWS。
- 数据基础设施预算：每月 5,000 美元（不含机器学习计算资源）。
- 管道可靠性 SLO 为 99%。

## 要求

产出一份 `DESIGN.md`（约 3,000 词及示意图），涵盖以下内容：

### 1. 架构图
清晰展示各组件及组件之间的数据流（ASCII、Mermaid 或 Excalidraw）。

### 2. 摄取策略
每个数据源如何进入管道？（S3 文件投递、Kinesis、PostgreSQL CDC 等。）说明各项选择的理由。

### 3. 处理层
批处理（Spark/EMR？Glue？Airflow + Pandas？），流式处理（Kinesis Analytics？EKS 上的 Flink？Kafka Streams？）。说明理由。

### 4. 存储层
Raw → Refined → Curated 分区，说明各层技术、保留期限与访问模式。

### 5. 编排
Airflow / Prefect / Argo Workflows / Dagster 等——选择并说明理由。

### 6. 可观测性
指标（什么）、日志（什么）、链路追踪（在哪里）、告警（哪些）。

### 7. 故障处理
摄取滞后、转换失败、上游 Schema 变化、Spark 作业 OOM 时分别会发生什么？

### 8. 成本模型
估算各组件月度成本，汇总得出预算建议。

### 9. 迁移路径
第 1 天最小可用管道 → 第 30 天完整管道 → 第 90 天完善版本。先构建什么，推迟什么。

### 10. 风险登记表
列出可能阻碍上线的五项主要风险及各自的缓解措施。

## 分步操作

### 步骤 1——盘点需求（30 分钟）
重新阅读场景，明确列出每项功能性与非功能性需求。

### 步骤 2——绘制组件草图（45 分钟）
绘制高层架构图。先不优化，只识别各组件。

### 步骤 3——说明每项技术选型的理由（60 分钟）
对每个组件写两句话说明理由。例如：「我们选择 Glue，因为团队已有使用经验，数据量低于每天 1TB，适合其无服务器模式；如果增长至每天 10TB，将切换至使用 Spot 的 EMR。」

### 步骤 4——故障模式分析（45 分钟）
针对每个组件询问：「它故障时会发生什么？」记录答案。包括部分故障（变慢但没有完全停止）。

### 步骤 5——成本表格（30 分钟）
使用 AWS Pricing Calculator，增加 20% 余量。

### 步骤 6——迁移计划（30 分钟）
梳理第 1 天至第 90 天的演进过程。能够创造价值的最小方案是什么？

### 步骤 7——风险登记表（15 分钟）
头脑风暴：Schema 漂移、厂商服务中断、人员流失、成本超支、安全事件。

## 交付物

1. `DESIGN.md`（单个文件，包含全部十个章节及图示）。
2. 成本电子表格 `COST.csv`。
3. `RISK_REGISTER.md`（也可以放在主文档中）。

## 验证

请同事评审并回答：
- [ ] 新工程师能否依据该文档完成构建，无需询问设计问题？
- [ ] 技术选择是否有理由，而非仅仅列举？
- [ ] 故障模式是否具体，而非仅说「我们会处理错误」？
- [ ] 成本是否符合预算？
- [ ] 是否明确了第 1 天的最小可用版本？

## 拓展目标

- 增加设计的**多区域**版本。
- 增加**厂商可移植性**分析：锁定程度如何？迁移需要多少成本？
- 邀请团队之外的人员开展**设计评审**，记录反馈。

## 常见陷阱

- **过度设计**——将第 90 天的设计当作第 1 天的设计。坚持最小方案优先。
- **技术选型堆砌**——选用五种不同的流处理器。选择一种，在适用范围内统一使用。
- **设计阶段忽略数据质量**——后续引入 GE 所需工作量可能是预先设计的三倍。
- **仅按按需价格估算成本**——多数生产管道可受益于预留、Spot 或承诺用量折扣。对不同购买方案均进行建模。
- **没有 SLO**——99% 可靠性 SLO 是设计的核心目标。否则每项设计决策都会被「万一发生什么」而非「为了什么」驱动。
