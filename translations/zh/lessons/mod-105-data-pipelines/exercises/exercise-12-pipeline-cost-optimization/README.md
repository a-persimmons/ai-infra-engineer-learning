# 练习 12：数据管道成本优化

**时长：** 3 小时
**难度：** 中级
**前置条件：** 练习 05 与 10

## 目标

对模块 105 中逐步构建的管道应用六种成本优化技术并测量节省金额：Spot 实例、列式格式与压缩、分区、文件大小调优、查询结果缓存，以及无服务器与常驻运行模式的选择。目标是在不损失功能的前提下降低 60% 成本。

## 为什么重要

数据管道的成本通常主要由三至五项构成：计算（Spark、dbt 数据仓库）、存储（S3 + Parquet）、查询（数据仓库额度或 Athena 扫描），以及数据传输（出站流量）。理解每个成本杠杆的工程师能够构建经济高效、可扩展的管道。

## 各系统的成本驱动因素

| 层级 | 成本驱动因素 | 典型账单项目 |
|---|---|---|
| 计算（Spark/EMR） | 实例类型 × 运行时长 × 实例数量 | EC2 |
| 计算（Glue/无服务器） | DPU × 运行时长 | Glue 作业 |
| 数据仓库（Snowflake/BigQuery） | 额度 × 扫描字节数或运行秒数（原文概括） | 计算额度 |
| 存储（S3） | GB × 月数 × 存储类别 | S3 Standard / IA / Glacier |
| 出站流量 | 跨区域或外部传输字节数 | 数据传输 |
| 格式 | Parquet、CSV、JSON、压缩 | 存储与扫描 |

## 要求

对管道应用每种技术，并测量优化前后的差异。

### 1. 压缩与列式存储
与 CSV 相比，使用 Snappy 压缩的 Parquet 通常可减少至原来的 1/5–1/10；只读取部分列的查询，扫描速度可能提高 5–50 倍。

### 2. 分区
Hive 风格分区裁剪。查询 `WHERE date = '2026-05-22'` 时只扫描该日期的数据。

### 3. 文件大小调优
Parquet 推荐文件大小示例：256–1024 MB。大量小文件增加列举开销；单个超大文件可能限制并行度。通过 `OPTIMIZE`（Delta）或重写作业合并小文件。

### 4. 批处理使用 Spot 实例
EC2 Spot 相比按需实例可能便宜 60–90%。管道必须能够容忍中断（检查点与恢复）。

### 5. 查询结果缓存
将热点聚合（例如练习 10 的 `dim_users`、`fct_user_daily_activity`）物化为表而非视图。每次 dbt 运行时重新计算，而非每次查询时计算。

### 6. 无服务器与常驻运行
原文建议：利用率低于约 30% 时，Glue / Athena / BigQuery 按需模式优于 EMR / Snowflake 常驻数据仓库；利用率高于 70% 时可能相反。实际应进行成本测量。

### 步骤 3——分区审计（30 分钟）

- 始终包含 `date` 谓词 → 按日期分区。
- 按用户查询 → 基数过高，不宜直接按用户分区；改用分桶。
- 有时进行全表扫描 → 考虑不分区（开销可能超过收益）。

### 步骤 5——批处理使用 Spot（30 分钟）
针对夜间 Spark 作业：
- EMR：使用包含多种实例类型的 Spot 实例队列，70% Spot + 30% 按需以提高稳定性。
- Glue：原文将其无服务器模式类比为隐式 Spot。

添加检查点：每五分钟保存进度，使 Spot 中断后能够恢复而非从头开始。

> 译注：Glue 无服务器计费不等同于 EC2 Spot；应区分 Glue Standard、Flex 等具体执行类别和价格。

### 步骤 6——物化策略审计（30 分钟）
针对每个 dbt 模型询问：
- 查询频繁、计算昂贵 → `materialized='table'`。
- 查询频繁、计算便宜 → `view` 即可。
- 查询较少 → `view` 或 `ephemeral`。
- 适合增量处理 → 优先考虑 `incremental`。

按矩阵调整，重新测量数据仓库额度消耗。

### 步骤 7——无服务器成本测试（15 分钟）
分别在 Glue（无服务器）与 EMR（常驻集群）运行一次管道。比较成本与运行时间。在 `COST_RECOMMENDATIONS.md` 中记录决策矩阵。

### 步骤 8——出站流量审计（15 分钟）
列出所有跨区域或跨云出站流量。逐项询问：能否移至同一区域？S3 跨区域复制的成本可能低于反复跨区域查询。

## 拓展目标

- 添加**自动化成本报告**：按管道、团队生成每周摘要与变化值。
- 实现**分层存储**：热数据使用 S3 Standard，温数据使用 Standard-IA，冷数据使用 Glacier，并配置生命周期规则。
- 开展**混沌成本测试**：在不同时段安排峰值任务，寻找非高峰时段的价格优势。

## 常见陷阱

- **过度分区**——按日期、小时、user_id 分区可能每天产生上千个分区，小文件数量激增。
- **Spot 中断但没有检查点**——长时间作业从头开始，反而增加净成本。
- **高利用率下切换至无服务器**——按秒计费在低占空比时可能更便宜，高占空比时可能更昂贵。
- **跨账号 S3 读取中的隐藏传输成本**——即使同区域跨账号读取，也应确认实际计费。
- **对 dbt 增量模型执行全量刷新**——一次 `--full-refresh` 可能在一小时内消耗此前一个月节省的额度。
