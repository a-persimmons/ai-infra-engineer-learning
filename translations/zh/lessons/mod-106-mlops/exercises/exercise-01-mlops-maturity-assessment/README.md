# 练习 01：MLOps 成熟度评估

**时长：** 3 小时
**难度：** 入门进阶
**前置条件：** 熟悉机器学习工作流

## 目标

使用公开的框架（Google 的 MLOps 成熟度等级）对真实或假设团队进行结构化成熟度评估，确定团队当前等级，按优先级排列接下来五项投入，并编写六个月路线图。

## 为什么重要

大多数「我们应该改善 MLOps」的讨论都比较模糊。成熟度评估将其转化为具体事项：「我们处于 Level 1；投资模型 CI/CD 能让我们进入 Level 2；以下是工作内容与顺序。」工程师和领导者都需要这样的明确性。

## 背景——成熟度等级

Google 广泛使用的框架：

- **Level 0**：全部手动操作。Notebook 驱动训练、复制粘贴部署，没有自动化。
- **Level 1**：自动化机器学习流水线（训练已流水线化，但模型部署仍为手动）。
- **Level 2**：流水线的 CI/CD（通过 CI/CD 部署流水线本身；持续产出新模型）。

原文将每个等级进一步划分为约 12 项子标准，涵盖人员、流程、技术和监控。

## 要求

1. 对团队进行四类**评分**：流程成熟度、工具、可靠性、治理。
2. **确定等级**（0、1 或 2），并给出理由。
3. **排列接下来五项投入的优先级**，分别分析成本与收益。
4. **编写六个月路线图**，包含里程碑。
5. **利益相关方摘要**（一页），面向非技术领导者。

## 分步操作

### 步骤 1——选择评估对象（15 分钟）
真实场景：你的团队或曾合作的团队。假设场景：「一家金融科技公司，五名工程师，三个生产模型，临时使用 Notebook 训练。」

### 步骤 2——依据评分标准打分（90 分钟）

使用以下评分表：

**流程成熟度**（1 = 临时处理，5 = 完全自动化）
- 代码版本管理：[ ]
- 数据版本管理：[ ]
- 实验追踪：[ ]
- 可复现性：[ ]
- 代码审查流程：[ ]
- 测试覆盖率：[ ]

**工具**（1 = 无，5 = 成熟）
- 流水线编排器：[ ]
- 特征存储：[ ]
- 模型注册中心：[ ]
- 监控技术栈：[ ]
- 部署自动化：[ ]
- 文档工具：[ ]

**可靠性**
- 已定义 SLO：[ ]
- 事故响应运行手册：[ ]
- 自动回滚：[ ]
- A/B 测试基础设施：[ ]
- 漂移检测：[ ]

**治理**
- 审计记录：[ ]
- 模型卡：[ ]
- 数据隐私控制：[ ]
- 偏差与公平性审查：[ ]
- 合规文档：[ ]

每项评分为 1–5 分，并给出书面理由（例如：「3——我们通过 MLflow 追踪实验，但没有管理数据版本。」）。

### 步骤 3——计算等级（15 分钟）
- 平均分低于 2 → Level 0。
- 平均分 2–3.5 → Level 1。
- 平均分高于 3.5 → Level 2。

> 译注：上述评分表及阈值属于本练习的评估方法，不是 Google 官方等级的认证规则。

### 步骤 4——前五项投入清单（45 分钟）
逐项说明弥补的缺口、预计投入（工程师周）和预期 ROI。按 ROI/工作量排序。

示例：
```
1. Add experiment tracking (MLflow) — 2 weeks — eliminates "what produced this number" debates
2. Codify a training pipeline (Airflow + dbt) — 6 weeks — moves Level 0 → Level 1
3. Add model registry + stage promotion — 3 weeks — replaces ad-hoc deploys
4. Implement drift monitoring — 4 weeks — catches degradation before it becomes incidents
5. Define SLOs for top 3 models — 1 week — anchor for production conversations
```

### 步骤 5——六个月路线图（30 分钟）
第 1–2 月：投入 1 + 2（基础建设）。
第 3–4 月：投入 3（部署流水线）。
第 5–6 月：投入 4 + 5（生产级能力）。

列出每个月的风险。

### 步骤 6——利益相关方一页纸摘要（15 分钟）
「现在在哪里、六个月后能达到哪里、需要花费多少、收益是什么。」面向管理者而非机器学习工程师编写。

## 验证

- [ ] 每项标准都有数字评分与一句理由。
- [ ] 前五项投入均引用评分标准中的具体缺口。
- [ ] 路线图里程碑符合 SMART 原则（具体、可衡量、可实现、相关、有时间限制）。
- [ ] 非技术人员能在三分钟内读完利益相关方摘要。

## 拓展目标

- 六个月后再次评估（真实或模拟），记录变化。
- 由三名不同队友分别评估，再协调差异。
- 构建其他团队可采用的**季度评审模板**。

## 常见陷阱

- **为了好看而打高分**——评分可适度保守；目标是发现值得投入的领域，而非显示自己已经完善。
- **泛泛的建议**——「实施 MLOps」不是具体建议。「在 2026-07-15 前添加 MLflow 以追踪推荐模型实验」才是。
- **忽略人员与流程**——仅投入工具而不改变评审、值班等流程，效果不佳。
- **没有获得支持的里程碑**——未经领导批准的路线图只是一份愿望清单。
