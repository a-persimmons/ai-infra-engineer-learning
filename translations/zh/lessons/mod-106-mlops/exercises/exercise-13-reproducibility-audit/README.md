# 练习 13：机器学习可复现性审计

**时长：** 2.5 小时
**难度：** 中级
**前置条件：** 练习 02、06（DVC）、03

## 目标

选取 30 天前训练的模型。不咨询同事，尝试精确复现其训练过程：相同数据、相同代码、相同依赖、相同超参数与相同输出。记录每个缺口，并利用这些缺口完善可复现性流程。

## 为什么重要

「你能复现这个结果吗？」是许多机器学习团队难以回答的问题。可复现性审计能够以较低成本发现缺口，避免监管人员或新加入的同事在更困难的情境中发现它们。

## 要求

针对一个生产中的模型：
1. **盘点**应当能够复现的内容。
2. **尝试**复现。
3. **评分**缺口（0 = 无法复现，1 = 接近，2 = 精确）。
4. **记录**每个缺口：缺少什么、如何弥补、工作量。
5. **实施**排名前三的缺口修复。

## 分步操作

### 步骤 1——选择目标（15 分钟）
一个当前处于 Production 的模型，最好由其他人于 30 天前训练。

### 步骤 2——盘点（15 分钟）
你需要复现：
- [ ] 代码（具体 commit）。
- [ ] 依赖（固定版本）。
- [ ] 训练数据（完全相同的数据行）。
- [ ] 超参数。
- [ ] 随机种子。
- [ ] 硬件（有时会影响浮点运算）。
- [ ] 训练环境（Docker 镜像、CUDA、驱动）。
- [ ] 输出：模型产物逐位一致，或指标差异在 ε 范围内。

### 步骤 3——尝试复现（60 分钟）
不询问任何人：
1. 找到 MLflow Run，记录标签及参数。
2. 从 MLflow 标签找到 Git SHA（找不到则明确记录失败）。
3. 检出该 SHA。
4. 找到该 SHA 对应的 Dockerfile / requirements。
5. 构建镜像。
6. 找到训练数据（DVC？已知前缀的 S3？查询？）。
7. 执行训练。
8. 比较输出（模型文件哈希、指标）。

每一步评分为 0/1/2。

### 步骤 4——记录缺口（30 分钟）
对于每个得分不是 2 的步骤：
- 缺少什么？
- 如何知道应该去哪里查找？
- 修复方案是什么？
- 需要多少工作量？

示例：
```markdown
## Gap 1: Data version
- Score: 0
- What's missing: MLflow run tags don't include the DVC commit hash. I found the parquet file in S3 but it had been overwritten since training.
- Fix: Add a tag `data_version: <dvc-sha>` to every training run; never overwrite data files (use versioned object storage).
- Effort: 1 day (training script change + S3 bucket versioning enable).

## Gap 2: Dependencies
- Score: 1
- What's missing: `requirements.txt` had `scikit-learn>=1.4`; at training time was 1.4.0, now 1.5.1.
- Fix: Use `requirements.lock` produced by `pip-compile`; commit and use in CI.
- Effort: 4 hours.
```

### 步骤 5——实施前三项修复（30 分钟）
选择影响最大的三个缺口。至少修复数据版本管理与依赖版本固定方面的缺口。

### 步骤 6——重新审计（15 分钟）
修复后，选取一个更近期的模型。复现并评分，与首次尝试的评分比较。

## 交付物

1. 首次复现尝试的 `AUDIT.md`。
2. 已实现的前三项修复（仓库中的提交）。
3. 修复后重新审计的 `AUDIT.md`。
4. `REPRODUCIBILITY_PLAYBOOK.md`：团队关于「可复现模型」的标准。

## 验证

- [ ] 首次审计发现至少三个缺口。
- [ ] 至少三项修复已经实施并合并。
- [ ] 对更新模型的重新审计显示改善。

## 拓展目标

- 在 CI 中添加**可复现性检查**：按需重建并重新训练；如果模型哈希不同则失败。
- 针对至少一个模型实现**逐位一致**复现测试（需要全流程确定性，比看起来更难）。
- 为每个模型产物添加**来源证明（Provenance Attestation）**（SLSA 风格，见 mod-103 ex-10）。

## 常见陷阱

- **GPU 浮点非确定性**——同样的代码和数据在不同 GPU 型号上可能生成略有差异的权重。逐位一致需要确定性配置（如 PyTorch 确定性模式）及适当的环境控制。
- **隐藏的环境依赖**——通过系统 pip 安装的包没有写入 requirements.txt。始终从干净容器开始。
- **可变训练数据**——未开启版本管理的 S3 存储桶覆盖了分区，旧数据丢失。对训练数据进行版本管理。
- **「在我的电脑上能运行」**——直到同事能依据你的修复复现结果，审计才算完成。

## 参考答案

没有统一的参考答案——每个团队的可复现性缺口都是独特的。

> 译注：即使开启确定性模式，也不能保证跨不同硬件、驱动和框架版本的逐位一致性。
