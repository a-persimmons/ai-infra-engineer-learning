# 练习 14：机器学习平台团队运营模式

**时长：** 3 小时
**难度：** 中级
**前置条件：** 练习 01 与组织背景

## 目标

设计或审视机器学习平台团队的运营模式：职责范围、提供的服务、需求受理流程、支持模式、值班轮换、成功指标。产出其他团队可以使用的「团队章程」。

## 为什么重要

如果没有人使用平台，技术卓越也无法产生价值。成功的机器学习平台团队具有明确的运营模式——负责什么、不负责什么、其他团队如何自助，以及如何处理例外情况。失败的团队可能技术很强，但运营职责含糊不清。

## 要求

产出 `CHARTER.md`（约 2,000 词），涵盖：

1. **使命**：一段话。
2. **职责范围**：平台负责什么、使用方负责什么（表格）。
3. **提供的服务**：每项服务的 SLO 与使用方式。
4. **需求受理流程**：用户如何请求能力、处理时效目标。
5. **支持模式**：支持层级、响应时间、升级机制。
6. **值班轮换**：排班、交接、呼叫策略。
7. **自助与工单**：哪些事项无需平台团队介入，哪些需要协助。
8. **成功指标**：团队如何衡量自身价值。
9. **年度路线图流程**：如何确定优先级。

## 分步操作

### 步骤 1——选择真实或假设组织（15 分钟）
真实：你当前的团队。假设：「一家拥有 200 名工程师的金融科技公司，四个产品团队共有 12 名机器学习工程师，一个四人平台团队。」

### 步骤 2——使命声明（15 分钟）
良好的使命声明说明做什么，也说明不做什么：

> 我们为机器学习训练、服务与可观测性提供自助基础设施。我们不构建模型——这是产品团队的职责；我们不负责数据质量——这是数据工程团队的职责。我们为两者提供支撑。

### 步骤 3——职责范围表（30 分钟）

| 能力 | 平台团队负责 | 产品团队负责 |
|---|---|---|
| 训练流水线编排 | 编排器（Airflow）及标准镜像 | DAG 内容与模型代码 |
| 模型服务基础设施 | K8s 集群、服务框架 | 模型镜像构建及部署清单 |
| 特征存储 | 基础设施 | 特征定义 |
| 监控 | Prometheus、仪表盘模板、告警基础设施 | 逐模型 SLO、告警阈值 |
| 成本归因 | 归因流水线 | 标签及查看自身账单 |
| 模型注册中心 | MLflow 与访问控制 | 注册与标签 |

### 步骤 4——服务与 SLO（30 分钟）

| 服务 | SLO | 使用方式 |
|---|---|---|
| 训练集群 | 99.5% 可用性 | 提交 Airflow DAG |
| 模型服务 | 99.9% 可用性，p95 低于 200ms | 使用我们的 Chart 执行 helm install |
| 特征存储 | 99.95% 可用性，读取 p99 低于 10ms | Feast SDK |
| 监控 | 99% 抓取可用时间 | 添加 `prometheus.io/scrape=true` 标记 |
| 成本报告 | 每日更新，UTC 09:00 前完成 | Athena 仪表盘 |

### 步骤 5——需求受理（15 分钟）
- 标准请求（职责范围内）：自助文档，预计无需平台团队投入工时。
- 非标准请求（新能力）：Slack + 表单 → 24 小时内分诊 → 纳入路线图或说明拒绝原因。
- 紧急请求（生产故障）：呼叫值班人员。

### 步骤 6——支持模式（30 分钟）
- **Tier 1**：自助文档 + Slack 频道，由轮换成员在 9:00–18:00 监看。
- **Tier 2**：提交工单；在工作时间口径下 24 小时内响应。
- **Tier 3**：呼叫值班人员；影响生产的问题在 30 分钟内响应。

### 步骤 7——值班（15 分钟）
- 四名工程师，每人值班一周，依次轮换。
- 呼叫来源：监控 SLO 违规、用户提交的 Tier 3 问题。
- 交接：每周轮换时举行 30 分钟会议。

### 步骤 8——自助与工单（30 分钟）
列出常见请求并为每项确定处理方式：

| 请求 | 模式 | 原因 |
|---|---|---|
| 将新模型部署到 staging | 自助 | 标准模式，已有文档 |
| 将特征添加到特征存储 | 自助 | PR 批准后自动完成 |
| 新训练集群 GPU 类型 | 工单 | 涉及容量规划与成本 |
| 研究项目的一次性计算资源 | 工单 | 需要提前了解需求 |
| 启动 LLM 服务端点 | 通过 Helm 自助 | 模式已经建立 |

### 步骤 9——成功指标（30 分钟）
- **采用率**：使用平台的产品团队数 / 总团队数。
- **交付速度**：从团队开始使用平台至首个模型上线的时间。
- **可靠性**：SLO 达成情况。
- **重复性运维工作（Toil）**：每周重复手动工作的小时数（目标：低于平台团队时间的 20%）。
- **满意度**：每季度收集产品团队 NPS。

### 步骤 10——路线图流程（30 分钟）
- 每季度：收集请求，依据成本与收益确定优先级。
- 一半容量：规划中的路线图工作。
- 25%：维持日常运行（重复运维、值班）。
- 25%：机会型工作（团队自主选择）。

## 交付物

1. 涵盖九个章节的 `CHARTER.md`。
2. 用于新请求的 `INTAKE_FORM.md` 模板。
3. `ONCALL_RUNBOOK.md`：值班要求及常见呼叫的初始响应。
4. `METRICS_DASHBOARD.md`：如何测量每项成功指标。

## 验证

邀请团队之外的同事阅读章程并确认：
- [ ] 能否正确提交请求？
- [ ] 能否自助部署模型？
- [ ] 是否知道谁在值班？
- [ ] 是否理解平台不会为他们做什么？

## 拓展目标

- 添加**需求门户**（小型 Web 应用），实现需求受理表单。
- 开展**利益相关方访谈**（五至十名产品团队成员），完善章程。
- 在外部发布章程，收集同行机器学习平台团队的反馈。

## 常见陷阱

- **职责范围蔓延**——每个产品经理都想要定制仪表盘。章程帮助你清楚地说明不予支持的原因。
- **没有 SLO**——每个问题都会变成紧急事件。定义并发布 SLO。
- **自助文档失实**——保持文档最新；无法执行的文档比没有文档更糟。
- **值班没有轮换**——容易导致个人过度负担。即使四人团队，也应进行每周轮换。
- **无人追踪成功指标**——如果没有测量，就无法了解指标。第一天就接入仪表盘。
