# 练习 03：深入 PromQL

**时长：** 2.5 小时
**难度：** 中级
**前置条件：** 练习 01–02；Prometheus 正在运行

## 目标

编写 25 条 PromQL 查询，覆盖即时向量、区间向量、聚合、直方图、记录规则与子查询，每条均针对运行中集群的真实指标。构建一份可以放在终端旁边的个人速查表 `PROMQL_CHEATSHEET.md`。

## 为什么重要

PromQL 是基础设施工程师最实用的查询语言之一。能够使用 PromQL 思考的工程师，比在 Grafana 中不断浏览面板、希望找到问题解释的工程师诊断得更快（原文举例为十倍）。

## 环境配置

运行 kube-prometheus-stack（参照 mod-101 实验 05），并对 iris-api 施加流量。现在你拥有真实的逐 Pod、逐 Namespace、逐集群指标。

## 25 条查询

针对每条查询，编写表达式，在 Prometheus 界面运行，截图或复制结果，并写一两句话说明其含义。

### Counter 与变化速率（1–5）

1. 过去一小时所有服务的 HTTP 请求总量。
2. 过去五分钟的每秒请求速率，按 HTTP 方法及状态码分组。
3. 过去十分钟流量最高的五个服务。
4. `irate` 与 `rate` 的区别——何时使用各自函数（用两句话比较，并通过突发流量模式演示）。
5. 过去两分钟的逐 Pod CPU 使用速率。

### 直方图与分位数（6–10）

6. iris-api 过去五分钟的 p50 延迟。
7. iris-api 过去五分钟的 p95 延迟，按 URL 路径分组。
8. p95 与 p50 的差异（延迟分散程度）。
9. 过去十分钟内有多少请求耗时超过 500ms？（原文建议使用 `histogram_count` 与桶过滤。）
10. SLI：耗时低于 200ms 的请求比例。

### 聚合与运算符（11–15）

11. 所有 Pod 的请求总数除以 Pod 数量（逐 Pod 平均值）。
12. 容器内存使用量占容器内存限制的百分比。
13. CPU 总使用量最高的三个 Namespace。
14. Predict_linear：按照当前变化速率，四小时后磁盘会有多满？
15. 某 Deployment 的所有 Pod 是否均为 Ready（label_join + group_left 技巧）。

### 子查询与记录规则（16–20）

16. 过去一小时内任意五分钟窗口的最大 p95 延迟（子查询）。
17. 计算过去一小时内的每分钟平均请求速率，再对过去 15 分钟取平均（嵌套聚合）。
18. 记录规则：以一分钟分辨率预计算逐路径请求速率。
19. 记录规则：每 30 秒计算一次整个集群的错误率。
20. 一条可借助第 18 项记录规则大幅加速的查询（原文目标为百倍加速）。

### 真实诊断（21–25）

21. 「哪个 Pod 正在大量占用 CPU？」——找出 CPU 使用量最高的三个 Pod。
22. 「我们在 14:00 发布了新版本，错误率是否变化？」——比较该时间戳前后一小时的错误率。
23. 「数据库是瓶颈吗？」——联合分析 API 延迟与数据库查询延迟。
24. 「重启次数在增长吗？」——对容器重启 Counter 使用 `changes()`，找出前十个 Pod。
25. 「当前错误预算消耗速率是多少？」——多窗口消耗速率告警查询（参照 mod-108 实验 05）。

## 分步操作

### 步骤 1——搭建环境（15 分钟）
确保 Prometheus + Grafana + iris-api 技术栈正在运行。产生持续负载（例如对 `/v1/predict` 执行 `wrk -t 4 -c 32 -d 1h`）。

### 步骤 2——完成查询 1–5（30 分钟）
截图，逐条记录笔记。

### 步骤 3——查询 6–10（直方图）（45 分钟）
直方图比较难。花时间理解桶的计算方法，使用已知真实值的合成数据验证分位数估计。

### 步骤 4——查询 11–15（45 分钟）
分组运算符（`group_left`、`group_right`）需要练习。使用 kube-state-metrics 中的真实标签集合。

### 步骤 5——查询 16–20（记录规则）（30 分钟）
将规则加入 Prometheus 配置，重新加载并验证。

### 步骤 6——查询 21–25（诊断）（30 分钟）
先将每项描述为真实运维问题，再编写查询。

### 步骤 7——汇总速查表（15 分钟）
在 `PROMQL_CHEATSHEET.md` 中记录凌晨三点值班时真正需要的十条查询。

## 常见陷阱

- **对 Gauge 使用 `rate()`**——通常没有合理含义；rate 适用于 Counter。对 Gauge 可使用 `delta`。
- **稀疏数据上的直方图分位数不准确**——原文认为每个桶不足 100 个样本时噪声较大。扩大时间窗口。
- **子查询成本高**——每个子查询会重复计算内部表达式；高频仪表盘优先使用记录规则。
- **忘记 `[5m]`**——直接读取 Counter 得到自进程启动以来的累计值。计算窗口内变化时使用 `rate()` 或 `increase()`。

> 译注：经典直方图可用总请求增量减去 le="0.5" 的累计桶增量计算超时数量；histogram_count 适用于原生直方图。重启次数宜用 increase 计算，changes 统计的是数值变化次数。记录规则通常通过 rule_files 引用独立文件。
